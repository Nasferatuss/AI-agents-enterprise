# Enterprise AI Agent Workbench — Knowledge Base

Это персональная вики-база знаний по проекту **Enterprise AI Agent Workbench**.
Паттерн: LLM инкрементально строит и поддерживает связанную markdown-вики поверх
неизменяемых первоисточников. Человек отвечает за источники, исследование и вопросы;
LLM делает всю рутину — summarizing, cross-referencing, filing, bookkeeping.

## Три слоя

1. **`sources/`** — первоисточники (PDF, статьи, заметки, транскрипты). **Immutable.**
   LLM читает их, но НИКОГДА не редактирует. Это source of truth.
2. **`wiki/`** — markdown-страницы, которые LLM полностью владеет: создаёт, обновляет,
   связывает, поддерживает консистентность. Человек только читает (в Obsidian).
3. **`CLAUDE.md`** (этот файл) — схема: структура вики, конвенции, workflow.
   Со-эволюционирует с человеком по мере того, как становится понятно, что работает.

## Язык и стиль

- Проза — **на русском**. Технические термины — **на английском**
  (RAG, eval, trace, orchestrator, guardrails, tool call, retrieval, и т.п.). Не переводить их.
- Кратко и плотно. Без воды. Каждая страница — для быстрого чтения и навигации.
- Тон: инженерный, по существу.

## Структура `wiki/`

```
wiki/
├── 00_index.md          # карта вики: оглавление, ссылки на всё, статус проекта
├── architecture/        # Service-Oriented Core + страница на каждый platform-слой
├── modules/             # одна страница на каждый из 10 demo-модулей
├── concepts/            # сквозные концепции: RAG, evals, MCP, observability, governance, context engineering…
├── decisions/           # ключевые решения + обоснование (ADR-стиль)
├── risks/               # риск-реестр, связанный с модулями и решениями
└── roadmap/             # фазы, спринты, KPI, метрики
```

## Конвенции страниц

- **Имена файлов**: `kebab-case.md`, латиницей, по сути страницы
  (`text-to-sql-rag-agent.md`, `service-oriented-core.md`).
- **Cross-links**: Obsidian-стиль `[[имя-файла-без-расширения]]`. Линковать щедро —
  ссылка на ещё несуществующую страницу это нормально, она помечает, что страницу стоит создать.
- **Frontmatter** на каждой странице:
  ```yaml
  ---
  type: module | architecture | concept | decision | risk | roadmap | index
  status: draft | active | done | deprecated   # для модулей/спринтов
  sources: ["Дорожная карта.pdf"]              # какие источники питают страницу
  updated: 2026-06-07
  ---
  ```
- **Секция Sources** внизу страницы: откуда взята информация (источник + где именно —
  страница PDF, секция). Это позволяет проверять и не терять провенанс.
- **Противоречия**: если новый источник противоречит тому, что уже в вики — НЕ затирать
  молча. Добавить блок `> ⚠️ Противоречие:` с обеими версиями и указанием источников.
  Синтез — это компромисс, который виден, а не переписанная история.

## Workflow

### Ингест нового источника
1. Положить файл в `sources/` (человек), либо LLM фиксирует ссылку/заметку.
2. Прочитать целиком. Для PDF использовать `pypdf` (см. ниже) — не полагаться на встроенный рендер.
3. Извлечь ключевые сущности, факты, решения, риски, метрики.
4. **Интегрировать, а не дублировать**: обновить существующие страницы там, где источник
   их дополняет; создать новые только для действительно новых сущностей.
5. Обновить cross-links и `00_index.md`. Проставить `updated:` и пополнить `sources:`.
6. Отметить противоречия со старым содержимым.

### Ответ на вопрос
1. Сначала искать ответ в `wiki/` (она уже синтезирована). Если есть — отвечать оттуда + ссылки.
2. Если в вики пробел — это сигнал: ответить из источников И дозаполнить соответствующую страницу.

### Поддержание
- После любого крупного изменения — проверить `00_index.md` и битые/недостающие ссылки.
- Держать `status:` модулей и спринтов в актуальном состоянии по мере прогресса.

## Извлечение текста из PDF

Встроенный рендер PDF требует poppler и может быть недоступен. Надёжный способ —
`pypdf` (установлен):

```bash
python3 - <<'EOF'
from pypdf import PdfReader
r = PdfReader("sources/ИМЯ.pdf")
for i,p in enumerate(r.pages):
    print(f"\n=== PAGE {i+1} ===\n{p.extract_text() or ''}")
EOF
```

## Принцип

Вики — это persistent, compounding артефакт. Cross-references уже на месте, противоречия
уже отмечены, синтез уже отражает всё прочитанное. С каждым источником и каждым вопросом
вики становится богаче. Знание компилируется один раз и поддерживается актуальным —
а не выводится заново на каждый запрос.
